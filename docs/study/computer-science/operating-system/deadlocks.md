# 死锁

## 死锁的起因

死锁产生的两个根本原因：

- **资源竞争**：多个进程竞争有限的不可共享资源
- **进程推进顺序不当**：进程请求和释放资源的顺序不合理，导致相互等待

## 系统模型

系统中有 $m$ 种资源类型 $R_1, R_2, \ldots, R_m$，每种资源 $R_j$ 有 $W_j$ 个实例。进程使用资源的过程分为三个操作：

1. **请求（Request）**：进程申请所需资源
2. 使用（Use）：进程占用资源执行工作
3. 释放（Release）：进程用完资源后释放

## 死锁的四个必要条件

死锁发生必须同时满足以下四个条件：

互斥（Mutual Exclusion）
: 资源必须被独占使用，即同一时刻只能有一个进程使用该资源。

占有并等待（Hold and Wait）
: 进程在持有至少一个资源的同时，又在等待获取其他被占用的资源。

非抢占（No Preemption）
: 已分配给进程的资源不能被强制剥夺，只能由进程主动释放。

循环等待（Circular Wait）
: 存在一个进程等待环：$P_1$ 等待 $P_2$ 占有的资源，$P_2$ 等待 $P_3$ 占有的资源，……，$P_n$ 等待 $P_1$ 占有的资源。

!!! warning "四个条件缺一不可"
    死锁的发生要求上述四个条件**同时成立**。只要破坏其中任一条件，死锁就不会发生——这正是死锁预防策略的理论基础。

## 资源分配图

资源分配图（Resource-Allocation Graph）是描述死锁的有力工具：

- **圆圈**：表示进程
- **方块**：表示资源类型（方块内的圆点表示该资源的实例）
- **请求边**（进程 → 资源）：进程正在请求该资源
- **分配边**（资源实例 → 进程）：该资源实例已分配给进程

???+ tip "环与死锁的关系"
    - 死锁 ⇒ 图中一定存在环
    - 环 ⇏ 死锁：环只是死锁的**必要条件**，不是充分条件
    - 当每种资源类型只有**一个实例**时，环 ⇔ 死锁
    - 当存在多个实例时，有环不一定死锁（因为环中某个进程可能最终获得资源并释放，打破循环等待）

## 死锁处理方法

| 方法 | 核心思想 | 代价 |
| --- | --- | --- |
| 死锁预防（Prevention） | 破坏四个必要条件之一 | 资源利用率低、系统吞吐量下降 |
| 死锁避免（Avoidance） | 动态检查资源分配，确保系统不进入不安全状态 | 需要先验信息（进程最大需求） |
| 死锁检测与恢复（Detection & Recovery） | 允许死锁发生，检测后恢复 | 检测开销、恢复可能导致数据丢失 |

!!! note "实际做法"
    大多数操作系统（如 UNIX、Windows）采用**鸵鸟策略（Ostrich Algorithm）**——直接忽略死锁问题。理由是死锁发生概率低，而预防和避免的代价过高，交由用户或管理员手动处理更经济。

## 死锁预防

死锁预防通过破坏四个必要条件之一来防止死锁发生：

| 条件 | 破坏方法 | 问题 |
| --- | --- | --- |
| 互斥 | 将资源设为共享（如只读文件） | 很多资源本质上不可共享（如打印机） |
| 占有并等待 | 进程在请求资源前必须释放所有已持有资源；或一次性申请所有资源 | 资源利用率低，可能饥饿 |
| 非抢占 | 若进程请求资源失败，则释放其持有的所有资源；或由系统强制抢占 | 实现复杂，可能导致数据不一致 |
| 循环等待 | 对资源类型线性排序，进程只能按序号递增顺序请求资源 | 限制请求顺序，可能造成资源浪费 |

## 死锁避免

死锁避免不事先破坏必要条件，而是在每次资源分配时**动态检查**是否可能导致死锁，只允许安全的分配。

### 安全状态

系统处于**安全状态**，当且仅当存在一个**安全序列** $P_1, P_2, \ldots, P_n$，使得对每个 $P_i$，它仍需请求的资源可以通过 $P_1, \ldots, P_{i-1}$ 释放的资源来满足。

- 安全状态 ⇒ 不会死锁
- 不安全状态 ⇏ 死锁（不安全状态只是可能死锁，不是必然死锁）

### 银行家算法

系统有 $n$ 个进程和 $m$ 种资源类型。定义以下数据结构：

- **Available**：长度为 $m$ 的向量，`Available[j] = k` 表示资源 $R_j$ 当前有 $k$ 个空闲实例
- **Max**：$n \times m$ 矩阵，`Max[i][j] = k` 表示进程 $P_i$ 最多需要 $k$ 个 $R_j$ 实例
- **Allocation**：$n \times m$ 矩阵，`Allocation[i][j] = k` 表示进程 $P_i$ 当前已分配 $k$ 个 $R_j$ 实例
- **Need**：$n \times m$ 矩阵，`Need[i][j] = Max[i][j] - Allocation[i][j]`，表示进程 $P_i$ 还需 $k$ 个 $R_j$ 实例

#### 安全性算法

用于判断系统是否处于安全状态：

1. 令 `Work = Available`，`Finish[i] = false`（$i = 0, 1, \ldots, n-1$）
2. 寻找满足 `Finish[i] == false` 且 `Need[i] <= Work` 的进程 $P_i$。若找不到，跳到第 4 步
3. 模拟 $P_i$ 完成并释放资源：`Work = Work + Allocation[i]`，`Finish[i] = true`，回到第 2 步
4. 若所有 `Finish[i] == true`，则系统处于安全状态；否则处于不安全状态

#### 资源请求算法

当进程 $P_i$ 请求资源时，设请求向量为 `Request_i`：

1. 若 `Request_i <= Need_i`，继续；否则报错（请求超过最大需求）
2. 若 `Request_i <= Available`，继续；否则 $P_i$ 等待（资源不足）
3. **试探性分配**：

    ```
    Available   = Available   - Request_i
    Allocation_i = Allocation_i + Request_i
    Need_i      = Need_i      - Request_i
    ```

4. 执行安全性算法检查试探分配后的状态：
    - 若**安全**：正式分配资源给 $P_i$
    - 若**不安全**：撤销试探分配，$P_i$ 等待

## 死锁检测

### 每种资源只有一个实例：等待图

当每种资源类型只有一个实例时，将资源分配图化简为**等待图（Wait-for Graph）**：

- 移除资源节点
- 将 `进程 → 资源 → 进程` 的两条边合并为一条 `进程 → 进程` 的等待边

等待图中**存在环 ⇔ 死锁**。

### 每种资源有多个实例

算法类似于银行家算法的安全性算法，但用 `Request` 矩阵替代 `Need` 矩阵：

1. 令 `Work = Available`，`Finish[i] = false`（若 `Allocation[i] == 0` 则 `Finish[i] = true`）
2. 寻找满足 `Finish[i] == false` 且 `Request_i <= Work` 的进程 $P_i$。若找不到，跳到第 4 步
3. 模拟 $P_i$ 完成：`Work = Work + Allocation[i]`，`Finish[i] = true`，回到第 2 步
4. 若存在 `Finish[i] == false`，则这些进程构成死锁集合

## 死锁恢复

检测到死锁后，需要打破死锁以恢复系统运行：

| 方法 | 说明 |
| --- | --- |
| 人工处理 | 操作员手动终止进程或重启系统 |
| 终止进程 | 逐个终止死锁进程直到打破循环；可选择终止代价最小的进程 |
| 资源抢占 | 从死锁进程中抢占资源分配给其他进程；需处理饥饿问题（确保同一进程不会持续被抢占） |

???+ info "终止进程 vs 资源抢占"
    - 终止进程代价高（已计算的工作丢失），但实现简单
    - 资源抢占可保留进程工作，但需要回滚机制，实现复杂，且可能导致被抢占进程饥饿
