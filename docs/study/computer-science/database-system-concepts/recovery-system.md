# 恢复系统

## 故障类型

事务故障（Transaction Failure）
: 逻辑错误（如违反约束）或系统错误（如死锁导致的回滚）。仅影响单个事务，需要回滚该事务。

系统崩溃（System Crash）
: 电源故障、操作系统或 DBMS 软件崩溃。内存数据丢失，但磁盘数据完好。需要重启后恢复未完成的事务。

磁盘故障（Disk Failure）
: 磁盘物理损坏导致数据丢失。需要从备份介质恢复。

## 恢复算法基本思路

恢复算法包含两个部分：

1. **正常操作期间**：记录日志、维护备份，为恢复做好准备
2. **故障发生后**：利用日志和备份将数据库恢复到一致性状态

## 存储结构

Volatile storage（易失性存储）
: 内存 / 缓存，系统崩溃后数据丢失

Non-volatile storage（非易失性存储）
: 磁盘 / SSD，系统崩溃后数据保留，但可能受磁盘故障影响

Stable storage（稳定存储）
: 通过 RAID 等冗余技术实现，即使磁盘故障数据也不丢失

## 数据访问机制

数据库访问涉及以下操作：

- `input(B)`：将磁盘块 B 读入内存缓冲区
- `output(B)`：将内存缓冲区块 B 写回磁盘
- `read(X)`：将缓冲区中的数据项 X 读入事务的私有工作区
- `write(X)`：将事务私有工作区中的数据项 X 写回缓冲区

???+ warning "不一致性风险"
    如果事务执行了 `write(X)`（修改已写入缓冲区），但在 `output(B)`（缓冲区写回磁盘）之前发生系统崩溃，则磁盘上的数据与缓冲区不一致——这正是恢复系统需要解决的问题。

## 日志恢复

### 日志格式

日志记录包含以下类型：

- `<Ti start>`：事务 $T_i$ 开始
- `<Ti, X, V_1, V_2>`：事务 $T_i$ 将数据项 X 从旧值 $V_1$ 修改为新值 $V_2$
- `<Ti commit>`：事务 $T_i$ 提交
- `<Ti abort>`：事务 $T_i$ 中止

### Undo 与 Redo

Undo 操作
: 将数据项恢复为旧值 $V_1$。用于处理未提交事务的修改。

Redo 操作
: 将数据项设置为新值 $V_2$。用于恢复已提交事务的修改。

两种操作都是幂等的——执行多次与执行一次效果相同。

判断规则：

- 事务未提交 → 对其修改执行 Undo
- 事务已提交 → 对其修改执行 Redo

## 事务回滚（正常操作）

当事务 $T_i$ 在正常操作期间需要中止时：

1. 从日志末尾向前扫描，找到 $T_i$ 的每一条修改记录
2. 对每条修改记录执行 Undo 操作，恢复旧值
3. 写一条补偿日志记录（CLR），记录 Undo 操作的内容
4. 继续扫描直到找到 `<Ti start>`，然后写入 `<Ti abort>`

CLR 的作用：如果恢复过程中再次需要回滚同一事务，CLR 可以避免重复扫描已经处理过的日志段。

## 检查点

检查点是定期记录的恢复参考点，用于缩小恢复扫描的范围：

1. 写入检查点记录，记录当前所有活跃事务
2. 将所有日志记录输出到稳定存储
3. 将所有修改过的缓冲块输出到磁盘

恢复示例：

- $T_1$：在检查点之前已提交 → **不需要处理**
- $T_2$：在检查点之前开始，检查点之后提交 → **从检查点开始 Redo**
- $T_3$：在检查点之前开始，检查点之后提交 → **Redo**
- $T_4$：在检查点之后开始，提交 → **Redo**

如果 $T_2$ 未提交（而是中止），则需要从 $T_2$ 的 `<T2 start>` 开始 Undo，而非从检查点开始。

## 系统崩溃后的恢复

系统崩溃后的恢复分为两个阶段：

### Redo 阶段

1. 找到最新的检查点记录
2. 从检查点开始**向前扫描**日志
3. 对所有遇到的操作执行 Redo（无论事务是否提交）
4. 维护 undo-list $L$：
   - 遇到 `<Ti start>` → 将 $T_i$ 加入 $L$
   - 遇到 `<Ti commit>` 或 `<Ti abort>` → 将 $T_i$ 从 $L$ 中移除

### Undo 阶段

1. 从日志末尾**向后扫描**
2. 对 undo-list $L$ 中事务的操作执行 Undo，并写入 CLR
3. 遇到 $T_i$ 的 `<Ti start>` → 写入 `<Ti abort>`，将 $T_i$ 从 $L$ 中移除
4. 当 $L$ 为空时停止

???+ info "恢复流程总结"
    Redo 阶段重建崩溃前的数据库状态，Undo 阶段回滚所有未完成事务。两个阶段配合确保数据库恢复到一致性状态。

## 日志缓冲

日志记录并非直接写入稳定存储，而是先写入内存中的**日志缓冲区**，再批量刷新到稳定存储。

日志缓冲区刷新条件：

- 日志缓冲区已满
- 事务提交时强制刷新（log force at commit）

### WAL（Write-Ahead Logging）规则

WAL 规则要求：与数据块修改相关的**所有日志记录必须先写入稳定存储**，然后才允许将对应的数据块写入磁盘。

WAL 是恢复系统正确性的关键保证——确保在数据块写入磁盘之前，相应的日志已安全保存，即使写入后立即崩溃也能通过日志恢复。
