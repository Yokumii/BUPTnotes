# E-R 模型与数据库设计

## E-R 模型基础

E-R（Entity-Relationship）模型是数据库概念设计的核心工具，通过对现实世界的实体、联系和属性的抽象，为后续的逻辑设计（关系模式）奠定基础。

## 实体集

**实体集（Entity Set）** 是同一类型的实体集合。例如，所有学生构成 `student` 实体集，所有课程构成 `course` 实体集。

<figure markdown="span">
  ![实体集](https://webp-pic.yokumi.cn/2025/10/20251028103220901.png){ loading=lazy width="70%" }
</figure>

### 弱实体集

**弱实体集（Weak Entity Set）** 没有足够属性形成唯一标识，必须依赖于一个**强实体集（Identifying/Strong Entity Set）** 才能存在。

- 弱实体集的存在依赖于强实体集（强实体集称为其**标识实体集**）
- 弱实体集与标识实体集之间通过**标识联系（Identifying Relationship）** 相连
- 弱实体集使用**分辨符/部分键（Discriminator / Partial Key）** 在同一强实体内区分不同弱实体
- 弱实体的完整主键 = 标识实体集的主键 + 分辨符

!!! abstract "弱实体集要点"
    - 弱实体集无法独立存在，其主键必须包含依赖的强实体集主键
    - 分辨符仅在同一个强实体范围内有区分能力，全局不唯一

## 属性

| 属性类型 | 说明 | 示例 |
| --- | --- | --- |
| Simple/Atomic（简单/原子） | 不可再分 | `age`、`gender` |
| Composite（复合） | 可分解为子属性 | `name = first_name + last_name`、`address = street + city + zip` |
| Single-valued（单值） | 每个实体只有一个值 | `student_id` |
| Multivalued（多值） | 每个实体可有多个值 | `phone_number`（一个人多个电话） |
| Derived（派生） | 可从其他属性计算得出 | `age` 可从 `date_of_birth` 推导 |
| Key（键） | 唯一标识实体 | `student_id` |

<figure markdown="span">
  ![复杂属性图示](https://webp-pic.yokumi.cn/2025/10/20251028105201207.png){ loading=lazy width="70%" }
</figure>

!!! tip "复合属性与多值属性的区别"
    - **复合属性**：一个属性由多个子属性组成（结构上的分解）
    - **多值属性**：同一个属性可以有多个取值（数量上的多值）

## 联系集

**联系集（Relationship Set）** 是同一类型联系的集合，连接两个或多个实体集。

<figure markdown="span">
  ![联系集](https://webp-pic.yokumi.cn/2025/10/20251028103342141.png){ loading=lazy width="70%" }
</figure>

### 联系集的属性

联系集本身也可以拥有属性。例如 `Takes` 联系集连接 `student` 和 `course`，可以附带 `Grade` 属性表示该学生在该课程中的成绩。

### 联系的度

**度（Degree）** = 参与联系集的实体集数量。

- 二元联系：2 个实体集参与（最常见）
- 三元联系：3 个实体集参与

### 映射基数

映射基数描述一个实体通过联系能关联多少个另一类实体：

| 映射基数 | 说明 |
| --- | --- |
| 1:1 | 一个 A 实体恰好关联一个 B 实体 |
| 1:N | 一个 A 实体可关联多个 B 实体，每个 B 只关联一个 A |
| N:1 | 多个 A 可关联同一个 B，每个 A 只关联一个 B |
| M:N | A 与 B 均可关联对方多个实体 |

## 设计过程

E-R 模型的设计通常遵循以下步骤：

1. **设计实体集**：识别现实世界中的核心对象类型
2. **设计联系集**：确定实体之间的关系及其映射基数和参与约束
3. **设计属性**：为实体集和联系集添加属性，确定属性类型（简单/复合/多值/派生/键）

!!! abstract "设计要点"
    - 先确定实体和联系，再细化属性
    - 联系集是否需要属性取决于业务语义（如成绩属于"选课"联系而非学生或课程本身）
    - 合理使用弱实体集避免人为添加冗余键属性

## 特化

**特化（Specialization）** 是自顶向下的设计过程：从高层实体集出发，根据特定特征划分为低层实体集。

- **不相交特化（Disjoint）**：低层实体集互不重叠，每个高层实体最多属于一个低层实体集
- **重叠特化（Overlapping）**：低层实体集可以重叠，一个高层实体可属于多个低层实体集
- **完全特化（Total）**：每个高层实体至少属于一个低层实体集
- **部分特化（Partial）**：并非每个高层实体都属于某个低层实体集

!!! tip "特化的图示"
    - 不相交用圆圈内写 **d** 表示
    - 重叠用圆圈内写 **o** 表示
    - 完全特化：高层实体集到特化圆用**双线**连接
    - 部分特化：高层实体集到特化圆用**单线**连接

## 泛化

**泛化（Generalization）** 是自底向上的设计过程：从多个低层实体集出发，提取共同特征形成高层实体集。

泛化与特化在 E-R 图中的表示结果相同，只是设计方向相反：

- 特化：从一般到特殊（top-down）
- 泛化：从特殊到一般（bottom-up）

## 聚集

**聚集（Aggregation）** 是一种高级抽象机制，将联系集作为实体对待，使其能参与更高层联系。

典型示例：`proj_guide(Student, Instructor, Project)` 是一个三元联系集，表示"某学生在某导师指导下做某项目"。现在需要对这个"指导关系"进行评价，形成 `eval_for` 联系集。此时 `proj_guide` 本身被聚集为一个实体参与 `eval_for`。

    聚集解决的核心问题是：当联系集本身需要作为实体参与其他联系时，如果不使用聚集，会导致三元联系与二元联系的混淆和冗余。

## 非二元联系转换为二元联系

任何非二元（三元及以上）联系都可以转换为二元联系：

1. 将原联系集 $R$ 提升为实体集 $E$
2. 创建新的二元联系集 $RA(E, A)$、$RB(E, B)$、$RC(E, C)$
3. $E$ 的属性包含原联系集 $R$ 的属性及各参与实体集的主键

<figure markdown="span">
  ![非二元联系转换为二元联系](https://webp-pic.yokumi.cn/2025/11/20251103151512645.png){ loading=lazy width="70%" }
</figure>

!!! tip "转换的优缺点"
    - 优点：统一为二元联系，简化模型结构
    - 缺点：可能引入冗余实体和属性，且可能丢失原有的映射基数约束信息

## E-R 模型到关系模式的转换

### 强实体集

直接映射为一个关系（表）：

- 实体集的每个属性对应表的列
- 主键 → 表的主键
- **复合属性** → 拆分为多个子属性列（不再保留复合属性本身）
- **多值属性** → 创建独立的关系表 $E_M$，包含实体主键 + 多值属性，主键为（实体主键，多值属性值）

### 弱实体集

映射为关系表，包含：

- 弱实体集自身的所有属性（含分辨符）
- 标识实体集的主键作为外键
- **主键 = 标识实体集主键 + 分辨符**

### 联系集

联系集的转换取决于映射基数：

| 映射基数 | 转换方式 | 主键 |
| --- | --- | --- |
| M:N | 新建关系表，包含参与实体主键 + 联系属性 | 参与实体主键的组合 |
| 1:N | 在"多"方实体表中添加外键（指向"一"方主键）+ 联系属性 | "多"方实体主键 |
| 1:1 | 选择一方作为"多"方，在其表中添加外键 + 联系属性 | 所选方实体主键 |

???+ warning "1:1 联系的处理"
    对于 1:1 联系，选择哪一方添加外键取决于参与约束：
    - 若一方为全部参与，优先在该方添加外键（避免 NULL 值）
    - 若双方均为部分参与，也可创建独立联系表

### 特化/泛化的转换

**方法 1：超类表 + 子类表**

- 超类实体集映射为一张表（包含所有共有属性）
- 每个子类实体集映射为一张表（仅包含子类特有属性 + 超类主键作为外键）
- 子类表与超类表通过超类主键关联

**方法 2：每个实体一张完整表**

- 每个子类映射为一张表，包含超类的所有共有属性 + 子类特有属性
- 超类不单独建表

!!! tip "两种方法的对比"
    | 方法 | 优点 | 缺点 |
    | --- | --- | --- |
    | 方法 1 | 无冗余，超类属性只存一次 | 查询子类需要连接超类表 |
    | 方法 2 | 查询子类无需连接 | 共有属性在多个子类表中重复存储 |

### 聚集的转换

聚集联系集映射为关系表，包含：

- 被聚集联系集的各参与实体主键（组成聚集的主键）
- 外键指向被聚集联系集对应的关系表
- 联系集的其他属性
