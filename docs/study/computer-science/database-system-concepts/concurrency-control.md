# 并发控制

## 锁协议

### 锁的类型

exclusive(X) 锁（排他锁 / 写锁）
: 事务对数据项 X 持有排他锁时，其他事务不能对 X 加任何锁。

shared(S) 锁（共享锁 / 读锁）
: 事务对数据项 X 持有共享锁时，其他事务可以对 X 加 S 锁，但不能加 X 锁。

## 两阶段锁（2PL）

两阶段锁协议将事务的锁操作分为两个阶段：

增长阶段（Growing Phase）
: 事务可以获取新锁、升级 S 锁为 X 锁，但不能释放任何锁。

收缩阶段（Shrinking Phase）
: 事务可以释放锁、降级 X 锁为 S 锁，但不能获取新锁。

???+ info "2PL 的性质"
    - 保证冲突可串行化：等价的串行顺序由各事务的**锁点（lock point）**——即增长阶段结束时刻——决定
    - 但 **不能防止死锁**：事务可能互相等待对方释放锁
    - 但 **不能防止级联回滚**：事务在收缩阶段释放 X 锁后，其他事务可能读到未提交数据

### 严格两阶段锁（Strict 2PL）

严格 2PL 要求事务持有的所有 **X 锁**必须等到事务提交或中止后才释放。这样可以防止级联回滚。

### 强严格两阶段锁（Rigorous 2PL）

强严格 2PL 要求事务持有的 **所有锁（S + X）**必须等到事务提交或中止后才释放。此时等价的串行顺序就是事务的提交顺序。同样可以防止级联回滚。

## 多粒度锁

锁可以加在不同粒度的数据对象上：表级、页级、行级、字段级等。

- 粒度越小 → 并发度越高，但锁管理开销越大
- 粒度越大 → 并发度越低，但锁管理开销越小

### 意向锁模式

意向锁用于在粗粒度上表示细粒度锁的意向，避免逐个检查细粒度锁的冲突：

IS（Intent Shared）
: 想在较低层级加 S 锁（意向读取子节点）

IX（Intent Exclusive）
: 想在较低层级加 X 锁（意向修改子节点）

S（Shared）
: 在当前节点加 S 锁（正在读取此节点）

X（Exclusive）
: 在当前节点加 X 锁（正在修改此节点）

SIX（Shared + Intent Exclusive）
: 在当前节点加 S 锁，同时在较低层级加 X 锁（正在读取此节点并修改子节点）

### 加锁规则

加锁顺序：从根到叶

- 加 S 锁或 IS 锁时，父节点必须持有 IS 或 IX 锁
- 加 X 锁、IX 锁或 SIX 锁时，父节点必须持有 IX 或 SIX 锁
- 必须遵循两阶段锁协议

解锁顺序：从叶到根

## 死锁

### 死锁预防

- **预先声明**：事务启动前声明所需全部锁，一次性获取
- **固定排序**：所有事务按固定顺序请求锁，破坏循环等待条件
- **超时机制**：等待超时则中止事务，简单但可能产生误判

### 死锁避免协议

wait-die 协议（非抢占式）
: 老事务等待新事务释放锁；新事务请求老事务持有的锁时，新事务直接中止（die）。

wound-wait 协议（抢占式）
: 老事务请求新事务持有的锁时，老事务伤害（wound）新事务——强制新事务中止并释放锁；新事务等待老事务释放锁。

???+ info "两种协议的区别"
    - wait-die：只有新事务被中止，老事务始终等待 → 非抢占式
    - wound-wait：只有新事务被中止，老事务抢占锁 → 抢占式
    - 两种协议都保证不会产生死锁，且不会产生循环等待

### 死锁检测

使用**等待图（wait-for graph）**检测死锁：

- 顶点：事务
- 边 $T_i \to T_j$：$T_i$ 正在等待 $T_j$ 释放锁

等待图中有环 → 存在死锁。

### 死锁恢复

选择牺牲事务（victim）的原则：

- 选择**回滚代价最小**的事务（考虑已执行的操作数量、涉及的数据项数量等）
- 避免饥饿：同一事务被反复选为牺牲者时，需要设置回滚次数的下限
