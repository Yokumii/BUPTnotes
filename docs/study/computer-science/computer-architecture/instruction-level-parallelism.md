# 指令级并行及其开发

## 基本概念

- **指令级并行（Instruction-Level Parallelism, ILP）**：指令之间存在一种并行性，利用它可以并行执行多条指令。
- 开发途径有 2 种：
    - 资源重复，重复设置多个处理部件；
    - 时间重叠，采用流水线技术；
    - 基于硬件的动态开发；
    - 基于软件的静态开发；
- **基本程序块**：一串连续的代码除了入口和出口以外，没有其他的分支指令和转入点。
    - 为了明显提高性能，必须跨越多个基本块开发 ILP。
- **循环级并行**：使一个循环中的不同循环体并行执行。
    - 循环展开（Loop Unrolling）技术；
    - 采用向量指令和向量数据表示；
- 再看相关和冲突：
    - 相关：**数据相关**、**名相关**、**控制相关**；
    - 冲突：**结构冲突**、**数据冲突**、**控制冲突**；
    - **相关是程序固有的一种属性**，反映了程序中指令之间的依赖关系；
    - 具体的一次相关是否会导致实际冲突以及冲突造成多长停顿，是**流水线的属性**；
- 对于正确地执行程序来说，必须保持**数据流**和**异常行为**：
    - 保持异常行为：无论怎么改变指令的执行顺序，都不能改变程序中异常的发生情况。
        - 常被弱化为：**指令执行顺序的改变不能导致程序中发生新的异常**。
    - 数据流：数据值从其产生者指令到其消费者指令的实际流动。
- 指令调度：
    - **静态指令调度**：编译器在编译时进行指令调度，减少相关和冲突，通过把相关的指令拉开距离来减少停顿。（第二章提到的方法）
    - **动态指令调度**：程序在执行过程中，依靠专门硬件对代码进行调度，减少数据相关导致的停顿；

## 指令的动态调度

在 5 段流水线的基础上，把译码阶段（ID）分为：

- **流出（Issue, IS）**：指令译码，检查是否存在结构冲突；
- **读操作数（Read Operands, RO）**：等待数据冲突消失，然后读操作数；

使得指令能**按序流出**，**乱序执行**，**乱序完成**。但是可能会导致 **WAR** 冲突和 **WAW** 冲突，例如：

```assembly
1. DIV.D F10, F0, F2
2. ADD.D F10, F4, F6
3. SUB.D F6 , F8, F14
```

其中，1 和 2 存在输出相关（WAW），乱序执行导致 2 可能先于 1 完成；2 和 3 存在反相关（WAR），乱序执行导致 3 可能先于 2 完成，破坏了数据流。为了解决这个问题，引入了**寄存器重命名**技术。

异常处理复杂化：不精确异常使得在异常处理后难以接着继续执行程序。

* **精确异常**：发生异常时，处理机的现场跟严格按程序顺序执行时指令 i 的现场相同。
* **不精确异常**：执行指令 i 导致发生异常时，处理机的现场（状态）与严格按程序顺序执行时指令 i 的现场不同。

## 动态调度算法

### 记分牌（Scoreboard）

#### 基本思想

* CDC 6600 处理机采用的算法；
* 记分牌负责相关检测并控制指令的流出和执行。
* 目标：**在没有结构冲突时，尽可能早地执行没有数据冲突的指令**，实现每个时钟周期执行一条指令。

#### 执行

1. **流出（Issue）**：如果当前流出指令所需的**功能部件空闲**，即不存在结构冲突，并且**所有其他正在执行的指令的目的寄存器与该指令的不同**（解决了乱序可能导致的 **WAW** 冲突），记分牌就向功能部件流出该指令，并修改记分牌内部的记录表。
2. **读操作数（Read Operands）**：记分派监测源操作数的可用性，如果可用，就通知功能部件从寄存器中读取源操作数并开始执行（动态解决了 RAW 冲突）。
3. **执行（Execute）**：指令在功能部件中执行，产生结果后，通知记分派执行完成。
4. **写结果（Write Result）**：记分牌知道指令执行完成后，检测是否存在**WAR** 冲突：
    - 如果没有，就允许指令写回目的寄存器，释放该指令占用的资源；
    - 如果有 WAR，就不允许，等待直到该冲突消失。
        - 前面的某条指令（按顺序流出）还没读操作数，且源操作数寄存器与该指令的目的寄存器相同，因此该指令不能写回目的寄存器。

#### 结构

<figure markdown="span">   ![](https://webp-pic.yokumi.cn/2026/06/20260619105202670.png){ loading=lazy width="70%" } </figure>

记分牌中记录的信息包括：

* **指令状态表**：记录每条指令进行到了哪个阶段；
* **功能部件状态表**：记录各个功能部件的状态，每个功能部件一项，每一项有 9 个字段：
    - Busy：功能部件是否空闲，初值为“no”，表示空闲；
    - Op：功能部件正在执行或将要执行的操作；
    - Fi：功能部件的目的寄存器编号；
    - Fj、Fk：功能部件的源寄存器编号；
    - Qj、Qk：功能部件的源寄存器的生产者，即向 Fj、Fk 写结果的功能部件；
    - Rj、Rk：为“yes”表示源寄存器 Fj、Fk 的值已就绪还未被取走，否则为“no”；
* **结果寄存器状态表**：每个寄存器一项，指出该寄存器的生产者，即向该寄存器写结果的功能部件。
    - 正在执行的指令都不以它作为目的寄存器，则为“no”；
    - 初值均为“no”；

#### 性能

记分牌的性能受限于以下几个方面：

- 程序代码中可开发的并行性，即是否存在可以并行执行的不相关的指令。
- **记分牌容量**：决定了流水线能在多大范围内寻找不相关指令。
    - **指令窗口**：流水线中可以同时容纳的指令数量。
- 功能部件的数目和种类。
- 名相关。

### Tomasulo 算法

#### 基本思想

* IBM 360/91 处理机采用的算法；
* 记录和检测指令相关，操作数一旦就绪立刻执行，把发生 RAW 冲突的可能性减少到最小；
* 通过寄存器换名消除 WAR 和 WAW 冲突：通过**保留站**和**流出逻辑**共同完成。
    - 当指令流出时，如果操作数还没计算出来，就将该指令中相应的寄存器名换名为将产生这个操作数的保留站的标识；
    - 指令流出到保留站后，其操作数寄存器号或者数据本身，或者换成了保留站的标识，不再与寄存器有关。
* **优点**：
    * 冲突检测和指令执行控制是分布的。
        * 通过保留站和 CDB 实现。
        * 计算结果由 CDB 直接从产生它的保留站传送到需要它的保留站，不用经过寄存器。
    * 消除了 WAW 和 WAR 冲突。
        * 通过寄存器换名和对操作数进行缓冲实现。

#### 结构

<figure markdown="span">   ![](https://webp-pic.yokumi.cn/2026/06/20260619114656941.png){ loading=lazy width="70%" } </figure>

* **指令队列**：存放部件送来的指令，FIFO，顺序流出。
* **保留站（Reservation Station）**：每个保留站中保存一条已经流出并等待到本功能部件执行的指令（相关信息）。包括：操作码、操作数以及用于检测和解决冲突的信息。
* **load 缓冲器和 store 缓冲器**：存放读/写存储器的数据或地址，类似于保留站。
* **公共数据总线 CDB**：所有功能部件的计算结果送到 CDB 上，由 CDB 把结果直接送到各个需要结果的地方。
    - 在具有多个执行部件且采用**多流出（即每个时钟周期流出多条指令）**的流水线中，需要采用多条CDB。
* **浮点寄存器**：通过一对总线连接到功能部件，并通过 CDB 连接到 store 缓冲器。
* **运算部件**：浮点加法器和浮点乘法器。

#### 执行

1. **流出（Issue）**：从指令队列的头部取一条指令
    * 如果该指令操作要求的保留站空闲，就把该指令流出到保留站 $r$。
        - 如果该指令的源操作数在寄存器中已就绪，就把它们送到保留站 $r$；
        - 如果该指令的源操作数还没有就绪，就把产生该操作数的保留站的标识送入保留站 $r$；
        - 被记录的保留站完成计算后，直接把结果送到保留站 $r$，而不经过寄存器。
        - 通过寄存器换名和对操作数进行缓冲，消除了 WAR 冲突。
    * 完成对目标寄存器的预约，消除 WAW 冲突。
    * 如果没有空闲的保留站，就不流出该指令，直到有空闲的保留站。
2. **执行（Execute）**：当指令的所有操作数都就绪后，保留站对应的功能部件就可以开始执行该指令。其中，load/store 指令的执行需要 2 个步骤：
    1. 计算有效地址（等待基地址寄存器就绪）
    2. 把有效地址放入 load/store 缓冲器中
3. **写结果（Write Result）**：指令执行完成后，功能部件把结果送到 CDB 上，CDB 把结果直接送到所有需要它的保留站（包括 store 缓冲器）和寄存器上。

#### 保留站字段

* Op：指令的操作码；
* Qj, Qk：产生源操作数的保留站标识；
    - 为 0 表示源操作数已就绪且在 Vj、Vk 中，或不需要操作数；
* Vj, Vk：源操作数的值；
    - 对于每一个操作数，V 和 Q 只有一个有效；
    - 对于 load 来说，Vk 用于保存偏移量；
* Busy：为“yes”表示该保留站正忙；
* A：仅 load / store 指令使用，存放指令中的立即数字段，地址计算完成后存放有效地址。

#### 寄存器状态表

* Qi：每个寄存器对应一项，存放把结果写入该寄存器的保留站编号；
    - 为 0 表示该寄存器中存放的值已就绪且在寄存器中，或没有正在执行的指令以该寄存器作为目的寄存器。

## 动态分支预测技术

### 基本概念

- **动态分支预测**：在程序**运行**时，根据分支指令过去的表现来预测其将来的行为。
- 有效性取决于：
    - 预测的准确性
    - 预测正确和不正确两种情况下的分支开销，进一步取决于：
        - 流水线结构
        - 预测方法
        - 预测错误时的恢复策略
- **目的**：
    - 预测分支是否成功
    - 尽快找到分支指令的目标地址或指令，避免控制相关造成的停顿

### 分支历史表 BHT

* **分支历史表（Branch History Table, BHT）**：记录分支指令最近一次或几次的执行情况，并据此进行预测，一般采用采用 2bits 记录历史：
    <figure markdown="span">   ![](https://webp-pic.yokumi.cn/2026/06/20260619135434263.png){ loading=lazy width="70%" } </figure>
    * 如图，只有连续两次分支执行情况相同，才会改变分支预测结果。
    * 分支预测：
        * 当分支指令到达译码段时，根据 BHT 中记录的历史信息进行预测。
        * 若预测正确，就继续处理后续指令，未断流；
        * 否则，作废已经预取和分析的指令，恢复现场，从另一条分支路径重新取指。
    * 状态修改；
* 缺点：
    - BHT 只判定分支是否成功，而不判定分支的目标地址；
    - 因此，BHT 只在判定分支是否成功所需的时间大于确定分支目标地址所需的时间时才生效。
    - 在经典 5 段流水线中，由于判定分支是否成功和计算目标地址都在 ID 段完成，因此 BHT 无法带来好处。

### 分支目标缓冲器 BTB

* 目标：将分支开销降为 0；
* 方法：分支目标缓冲
    * 将分支成功的**分支指令地址**和**分支目标地址**放到一个缓冲区保存，缓冲区以**分支指令的地址**作为标识；
    * 缓冲区即为分支目标缓冲器（Branch Target Buffer, BTB）；
* 结构：

* 操作：
    <figure markdown="span">   ![](https://webp-pic.yokumi.cn/2026/06/20260619141118114.png){ loading=lazy width="70%" } </figure>
* BTB各种情况下的延迟：
    <figure markdown="span">   ![](https://webp-pic.yokumi.cn/2026/06/20260619142531516.png){ loading=lazy width="70%" } </figure>
    * 这相当于一个cache的缓存机制，记录成功分支指令，下一次指令来到时便会先与BTB进行匹配，如果匹配主键就直接获得成功分支目标地址，因此没有造成停顿；
    * 如果找不到，或者预测与实际相反，就需要**先花一个周期更新 BTB，再花一个周期重新取指令，因此造成 2 个周期的停顿**。

### 基于硬件的前瞻执行

* 基本思想：对分支指令的结果进行猜测，并假设这个猜测总是对的，然后按这个猜测结果继续取、流出和执行后续的指令。只是执行指令的结果不是写回到寄存器或存储器，而是写入一个称为**再定序缓冲器 ROB（ReOrder Buffer）**中。等到相应的指令得到“确认”（Commit）（即确实是应该执行的）之后，才将结果写入寄存器或存储器。
* 对 Tomasulo 算法加以扩充，就可以支持前瞻执行：
    * 将写结果分为 **写结果** + **指令确认**
    * 允许乱序执行，但**必须顺序确认**。

ROB 项的字段包括：

* 指令类型；
* 目标地址：给出指令执行结果应写入的目标寄存器号（如果是 load / ALU 指令）或存储器单元的地址（如果是 store 指令）；
* 数据值字段；
* 就绪字段；

每条指令在被确认之前在 ROB 中都有相应的一项，所以**执行结果是用 ROB 项的编号作为标识**的，而不再用保留站编号。

* 优点：
    * 通过 ROB 实现了指令的顺序完成；
    * 能够实现**精确异常**，即使发生异常，也能保证程序的正确执行；
    * 容易推广到整数寄存器和整数功能单元上；
* 缺点：硬件实现复杂；

## 多指令流出技术

一个时钟周期内流出多条指令，使得理想 CPI < 1。

<figure markdown="span">   ![](https://webp-pic.yokumi.cn/2026/06/20260619144356402.png){ loading=lazy width="70%" } </figure>

* 多流出处理机：
    * **超标量处理机**（Superscalar Processor）：
        - 每个时钟周期流出指令条数**不定**，但存在上限 n，对应 n-流出。
        - 由编译器或硬件完成调度。
    * **超长指令字处理机 VLIW**（Very Long Instruction Word Processor）：
        - 每个时钟周期流出的指令条数**固定**，实际上由多个单操作指令构成一个超长指令，称为一个**指令包**。
        - 指令包中，指令间的并行性可以通过指令显式表达；
        - 由**编译器（静态）**调度；

<figure markdown="span">   ![](https://webp-pic.yokumi.cn/2026/06/20260619145128974.png){ loading=lazy width="70%" } </figure>

### 基于静态调度的多流出技术

1. 在取指令阶段，流水线将从取指令部件收到 1 ~ n 条指令（称为**流出包**）；
2. 流出部件检测结构冲突或数据冲突，一般分 2 阶段实现：
    1. **第一段**：进行流出包内的冲突检测，选出初步判定可以流出的指令；
    2. **第二段**：检测所选出的指令与正在执行的指令是否有冲突。

MIPS处理机实现超标量方法：

* 同时取 2 条指令，译码 2 条指令（**1 条整数型指令 + 1 条浮点操作指令**）
    <figure markdown="span">   ![](https://webp-pic.yokumi.cn/2026/06/20260619152731721.png){ loading=lazy width="70%" } </figure>
    * 需要增加的硬件很少；
    * 浮点 load / store 使用整数部件，会增加对浮点寄存器的访问冲突。
        - 解决方法：增设一个浮点寄存器的读/写端口
    * 由于流水线中的指令多了一倍，定向路径也要增加。
* 限制超标量流水线的性能发挥的障碍：
    * load 指令：load 指令要求后续 3 条指令都不能使用其结果，否则就会引起停顿。
    * 分支延迟；

静态调度的**缺点**：

* 有相关就停止流出；
* 代码与超标量处理机结构有关；

### 基于动态调度的多流出技术

* 扩展 Tomasulo 算法，使其支持多流出：
    * 每个时钟周期流出 2 条指令；
    * 一条是整数型指令，一条是浮点型指令；
* 指令按顺序流向保留站，否则会破坏语义。
* 整数使用的表结构和浮点使用的表结构分别进行处理，这样同时流出的两条指令到各自保留站。
* 实现多流出的两种的方法：
    * 在半个时钟周期里完成流出步骤，这样一个时钟周期就能处理两条指令。
    * 设置一次能同时处理两条指令的逻辑电路。

### 超长指令字技术

* 执行过程：
    1. 把能并行执行的多条指令组装成一条很长的指令；
    2. 设置多个功能部件；
    3. 指令字被分割为一些字段，每个字段被称为一个**操作槽**，直接独立控制一个功能部件；
    4. 在VLIW处理机中，在指令流出时不需要进行复杂的冲突检测，而是依靠**编译器**全部安排好了。
* 存在的问题：
    * 程序代码长度增加，**目标代码编码效率低**
        * 提高并行性而增加大量循环展开
        * 指令字中的操作槽并非总能填满
        * 解决方法：指令共享立即数字段 / 指令压缩存储 / 调入 Cache / 译码时展开
    * 采用了**锁步**机制：任何一个操作部件出现停顿时，整个处理机都要停顿。
    * 机器代码的不兼容性，**目标代码兼容性差**

### 超标量处理机 vs. 超长指令字处理机

- 超标量处理机对程序员**透明**，处理机能自己检测下一条指令是否能流出，不需要由编译器或专门的变换程序对指令进行重排；
- 超标量处理机即使没有经过编译器针对超标量结果进行调度优化的代码也能够运行，不过效果不会很好。
- 在动态调度的超标量处理器中，相关检测和指令调度是由**硬件**完成的；
- 在静态调度的超标量处理器中，相关检测和指令调度是由**编译器**完成的；
- 在超长指令字处理机中，相关检测和指令调度全部由**编译器**完成的。

总结：

* 超标量 Superscalar 处理机：
    * 代码量较小
    * 二进制兼容性好
* VLIW 处理机：
    * 译码、发射指令的硬件设计简单
    * 需要访问更多寄存器，一般使用多个寄存器文件

### 超流水线处理机

* 将每个流水段进一步细分，这样在一个时钟周期内能够分时流出多条指令。
    * 超标量处理机：空间并行性
    * 超流水线处理机：时间并行性
* 对于一台每个时钟周期能流出 $n$ 条指令的超流水线处理机来说，这 $n$ 条指令不是同时流出而是每隔 $\frac{1}{n}$ 个时钟周期流出一条指令。例如

## 例题

??? info "例题 1"
    设指令流水线由取指令、分析指令和执行指令三个部件构成，每个部件经过的时间为 $\Delta t$，连续流入 12 条指令。分别画出标量流水处理机以及 ILP 均为 4 的超标量处理机、超长指令字处理机、超流水处理机的时空图，并分别计算它们相对于标量流水处理机的加速比。

    解答：

    * 标量流水处理机：
        <figure markdown="span">   ![](https://webp-pic.yokumi.cn/2026/06/20260619164416429.png){ loading=lazy width="70%" } </figure>
        * $T_k = 3\Delta t + (12 - 1)\Delta t = 14\Delta t$
    * 超标量处理机：
        <figure markdown="span">   ![](https://webp-pic.yokumi.cn/2026/06/20260619164633837.png){ loading=lazy width="70%" } </figure>
        * $T_k = 3\Delta t + (12 / 4 - 1)\Delta t = 5\Delta t$
        * 加速比 $S = \frac{14\Delta t}{5\Delta t} = 2.8$
    * 超长指令字处理机：
        <figure markdown="span">   ![](https://webp-pic.yokumi.cn/2026/06/20260619164937131.png){ loading=lazy width="70%" } </figure>
        * 12个任务组装成3条长指令，每条含4条小指令。
        * 总执行时间和加速比同上。
    * 超流水线处理机：
        <figure markdown="span">   ![](https://webp-pic.yokumi.cn/2026/06/20260619165033605.png){ loading=lazy width="70%" } </figure>
        * 可以把时钟周期看作 $\Delta t / 4$，相应的段数也变为 $3\times 4 = 12$
        * $T_k = （12 + 12 - 1）\Delta t / 4 = 5.75\Delta t$
        * 加速比 $S = \frac{14\Delta t}{5.75\Delta t} = 2.435$
